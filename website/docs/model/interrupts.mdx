# Interrupts & resume

*Normative: [MODEL.md §6](/reference/spec).*

> **An interrupt is a step whose value comes from a human instead of a function.**

That single idea gives the whole human-in-the-loop feature set for free.
`ctx.interrupt(payload)`:

1. Look the key up in the journal. **Hit** → return the recorded answer.
2. **Miss** → journal `{ key, pending, payload }`, then **halt the task**.

Halting a task halts its superstep: the engine checkpoints (journals included),
emits an `interrupt` event carrying the payload, and ends the run. The thread now
has a **pending interrupt**. The next run for that thread must supply an answer;
the engine writes it into the journal entry and replays the task.

<Tabs groupId="lang">
<TabItem value="ts" label="TypeScript">

```ts
import { graph, channel, START, END, run, resume, InMemoryCheckpointer } from "@ilmek/core";
import type { ChannelMap, StateOf } from "@ilmek/core";

/** Support state — one append-only channel of messages. */
const SupportState = {
  messages: channel.append<string>(),
} satisfies ChannelMap;

type SupportState = StateOf<typeof SupportState>;

const g = graph("support", SupportState)
  .node("agent", async (state, ctx) => {
    // First pass halts here; the resume pass returns the human's answer.
    const answer = await ctx.interrupt<string>({ question: "Approve purchase?" });
    return { messages: [`approved: ${answer}`] };
  })
  .edge(START, "agent").edge("agent", END)
  .compile();

const opts = { threadId: "conv-42", checkpointer: new InMemoryCheckpointer() };

const paused = await run(g, { messages: ["buy"] }, opts);  // status: "interrupted"
const done = await resume(g, "yes", opts);                 // status: "done"
```

```csharp
var buy = Update.For<SupportState>().Append(s => s.Messages, "buy");

var done   = await g.ResumeAsync("yes", opts);   // Status: Done
```

## Everything falls out of the journal

None of the following is special-cased — each is a direct consequence of the
[journal](/model/journal):

- **Multiple pauses per node** — each `interrupt` has its own key; each resolves
  once; replay fast-forwards through the already-answered ones. No index-matching.
- **Pauses inside loops** — work, given [stable keys](/model/journal#keys).
- **Concurrent interrupts** — two tasks in one superstep may both halt pending;
  the run emits both and resumes both when both are answered.
- **Effects before a pause never re-run.**
- An interrupt is a **first-class control signal**, never an exception smuggled
  through an error channel. Consumers never inspect error strings to discover a
  pause.

## `id` vs `key`

*This is the one wrinkle worth knowing up front.*

A journal key is unique **within its task** and nowhere else. Two nodes that each
call a bare `interrupt` in the same superstep therefore *both* journal
`interrupt#0` — each task counts occurrences on its own. So a pending interrupt
carries two handles:

| Field | Scope | Used for |
|---|---|---|
| `key` | the task (`"interrupt#0"`) | addressing the journal entry |
| `id` | the thread (`"<node>:<key>"`) | addressing the pause from outside |

For a task started by a [`send`](/control-flow/send), the node part of the `id`
is its task key, so two fan-out branches pausing in the same superstep get
distinct ids: `worker#0:interrupt#0`, `worker#1:interrupt#0`. A pending
interrupt also carries `taskId`, `node` and the `payload` the node passed.

**Resume answers must be keyed by `id`.** Keying by `key` looks fine until the
first concurrent pause, then silently drops an answer and hands both nodes the
same one — a data-corruption bug with no error.

A second argument names the key yourself — `ctx.interrupt(payload, "approve")`
journals `approve#0` — which makes the `id` readable (`confirm:approve#0`) and is
how a loop gives each pause a [stable key](/model/journal#keys).

## Two resume forms

Which form applies is decided by the **number of pending interrupts**, never by
the answer's own type:

- **bare answer** — legal only when exactly one interrupt is pending. Because the
  *count* decides, an object answer (`{ approved: true }`) can never be mistaken
  for a key map.
- **keyed answers** — a map of `id => answer`. Works for any count, so a UI that
  renders every open pause needs no special case for "exactly one".

Auto-suffixing makes the bare form safe even for several pauses in one node:

<Tabs groupId="lang">
<TabItem value="ts" label="TypeScript">

```ts
import { graph, channel, START, END, run, resume, InMemoryCheckpointer } from "@ilmek/core";
import type { ChannelMap, StateOf } from "@ilmek/core";

/** Danger state — an append-only log of what was confirmed. */
const DangerState = {
  log: channel.append<string>(),
} satisfies ChannelMap;

type DangerState = StateOf<typeof DangerState>;

const g = graph("danger", DangerState)
  .node("confirm", async (state, ctx) => {
    const ok   = await ctx.interrupt({ question: "Delete production?" });   // interrupt#0
    const sure = await ctx.interrupt({ question: "Really sure?" });         // interrupt#1
    return { log: [`deleted: ${ok} / ${sure}`] };
  })
  .edge(START, "confirm").edge("confirm", END)
  .compile();

const opts = { threadId: "conv-42", checkpointer: new InMemoryCheckpointer() };

// One interrupt is pending at a time, so the bare-answer form stays safe
// even though the node pauses twice.
await run(g, {}, opts);                       // halts on interrupt#0
await resume(g, "yes", opts);                 // answers #0, halts on interrupt#1
const done = await resume(g, "yes", opts);    // answers #1 → status: "done"
```

When several pauses are open at once — two nodes pausing in the same superstep —
read them with `pendingInterrupts` and answer them together, keyed by `id`:

<Tabs groupId="lang">
<TabItem value="ts" label="TypeScript">

```ts
import { graph, channel, START, END, run, resumeKeyed, pendingInterrupts, InMemoryCheckpointer } from "@ilmek/core";
import type { ChannelMap } from "@ilmek/core";

/** Review state — an append-only log of the sign-offs. */
const ReviewState = {
  log: channel.append<string>(),
} satisfies ChannelMap;

const g = graph("review", ReviewState)
  .node("legal", async (state, ctx) => ({ log: [`legal: ${await ctx.interrupt<string>({ question: "Legal OK?" })}`] }))
  .node("finance", async (state, ctx) => ({ log: [`finance: ${await ctx.interrupt<string>({ question: "Budget OK?" })}`] }))
  .edge(START, "legal").edge(START, "finance")
  .edge("legal", END).edge("finance", END)
  .compile();

const checkpointer = new InMemoryCheckpointer();
const opts = { threadId: "deal-7", checkpointer };

await run(g, {}, opts);                                     // both nodes pause in one superstep
const pending = await pendingInterrupts(checkpointer, "deal-7");
console.log(pending.map((p) => p.id));                      // [ "legal:interrupt#0", "finance:interrupt#0" ]

const done = await resumeKeyed(g, { "legal:interrupt#0": "yes", "finance:interrupt#0": "approved" }, opts);
console.log(done.status, done.state?.log);                  // "done" [ "legal: yes", "finance: approved" ]
```

A few guardrails keep a thread from being driven the wrong way, each a
`ResumeError` (`ResumeException` in .NET) with a message naming what to do
instead:

- a plain `run()` on a thread that is parked on a pause is refused — it would
  drop the pause; answer it with a resume;
- a resume on a thread with no checkpoint, or one that is not parked, is refused;
- a bare answer while more than one interrupt is pending is refused, and the
  message lists the ids to answer with `resumeKeyed`;
- `ctx.interrupt()` in a run without a checkpointer is refused — the pause has
  nowhere to be stored.

## A resume is all-or-nothing, and safe to retry

A keyed resume is checked as a whole before anything is written: if one pending
`id` has no answer, the call is refused with a `ResumeError` naming it and **no**
answer is recorded, so the corrected call simply works. Answers for ids that are
not pending are ignored.

The answer is journaled before the resumed superstep runs. If that superstep
does not commit — a node throws, the run is aborted, the process dies — the
thread is still parked on the same pause, and you resume it again:

- the **same** answer (deep-equal) replays: the superstep runs again, and every
  step that already completed — including steps after the pause — comes back
  from the journal instead of re-running;
- a **different** answer is refused with a `ResumeError`. Steps after the pause
  may already have acted on the first answer, so it cannot be swapped out
  underneath them.

## Known limitations

Documented rather than fixed — know them before you build on them:

- **Concurrent resumes of one pause.** The [checkpointer port](/checkpointers/overview#the-port)
  has no compare-and-swap, so two resumes of the same parked thread that race
  each other both run the resumed superstep. A step *before* the pause still runs
  exactly once, but a step *after* it can run twice. Serialize resumes per
  thread in your host — a queue or a lock keyed by thread id.
- **`:` in node names or interrupt keys.** An `id` is `<node>:<key>`, so node
  `a:b` pausing on key `c` and node `a` pausing on key `b:c` in the same
  superstep produce the same id. Keep `:` out of node names and interrupt keys.
- **A re-raised pause reports a different payload in each language.** When a
  replay reaches a pause that is still journaled as pending — say a superstep
  that paused in one task and failed in another is run again — TypeScript reports
  the payload the node passes on this pass, .NET the payload journaled when the
  pause was first raised. They differ only when a node builds its payload
  nondeterministically, which the [contract](/model/journal#the-contract)
  already rules out.
- **.NET: an answer of the wrong type.** `InterruptAsync<int>` answered with
  `"x"` fails the node with `InvalidCastException` — and since the answer is
  already journaled, the thread then accepts only that same answer. Validate an
  answer's type before resuming with it.
- **Postgres cannot store U+0000** in a payload, answer or step value — see the
  [Postgres checkpointer](/checkpointers/postgres#values-postgres-cannot-store).
- **.NET: typed step results with a durable checkpointer.** A step that returns
  a record or tuple replays fine from `InMemoryCheckpointer` but not from SQLite —
  see [Serializable values](/model/journal#serializable-values).
